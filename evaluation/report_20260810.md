# XBot HarnessBench 评估报告（2026-08-10）

## 摘要

当前结果目录 `harnessbench-xbot-m3-26f346` 已覆盖全部 106 个官方
HarnessBench 任务。按 sample ID 合并四份 Inspect 日志，并以最后一次有效评分
覆盖早期中断记录后，106 个任务均有数值评分，没有剩余的取消、无评分或零分
任务。因此，该目录在“可汇总评分”意义上已经完成。

当前 XBot 平均分为 **0.8242**，较原始完整基线 `0.7814` 提高
**0.0428**，但低于 `harnessbench-xbot-m3-26f346_old` 的 **0.8617**。
OpenCode 在相同 106 个任务上的平均分为 **0.8405**，领先当前 XBot
**0.0163**。这一配对差值的近似 95% 区间为 **[-0.0053, 0.0379]**，跨过
零点，因此单次评估不足以证明两个框架在总体任务质量上存在明确差异。

XBot 最稳定的进步是工具执行可靠性：ACP 工具失败率从基线的 **14.79%**
降至旧版 Docker 结果的 **6.32%**，当前进一步降至 **3.08%**。OpenCode
仍然更低，为 **0.82%**，且使用了明显更少的模型 token。

本报告属于工程诊断，而不是严格受控的基准结论。当前 XBot 结果由四次续跑
合并而成，包含两种 timeout 语义；现有 OpenCode 结果则运行于主机环境，而非
当前 Docker 环境。

## XBot 纵向变化

### 原始基线到 XBot old

旧版 Docker 结果是现有证据中 XBot 得分最高的一次：

- 平均分从 0.7814 提升至 0.8617，增加 **0.0804**。
- 106 个配对任务中，45 项提高、16 项下降、45 项持平。
- 配对差值近似 95% 区间为 **[0.0442, 0.1166]**。
- 软件工程类提高 **0.1469**，工作区/工具/多模态类提高 **0.1121**，是
  增幅最大的两个类别。
- 工具失败数从 298 降至 135；代价是总 token 增加 45.2%，sample 总耗时
  增加 23.1%。

提升最大的任务包括 `013-image-edit`（+1.0000）、`009-git-pr-merge`
（+0.7500）、`087-cli-parser-bug-tests`（+0.7000）和
`052-metric-definition-audit`（+0.6588）。

## 完整性审计

当前 XBot 目录需要按修改时间合并日志，并对同一 sample ID 采用最后一次有效
评分：

1. 第一份日志包含 87 个有效评分和 4 个被取消的 sample 记录。
2. 第二份日志按新的 task identity 续跑 19 个指定任务。
3. 第三份日志用成功评分覆盖 `013-image-edit`。
4. 第四份日志用成功评分覆盖被取消的 `085`、`086`、`088`、`089`。

合并后恰好包含 106 个官方 ID 和 106 个数值评分，早期取消记录均被后续有效
记录覆盖。

但这不是一次同质全量运行。第一段采用固定的 Inspect Task `2400s` 限制；后续
分段采用 HarnessBench 的 per-case、per-Agent-round 限制。目录中的
`run-manifest.json` 会被每次定向续跑覆盖，因此目前只描述最后四个 sample 的
调用，不能完整描述整个合并结果；早期每一段的精确 commit 和镜像信息已经无法
从该 manifest 恢复。

## 结论

1. XBot 相对原始基线存在明确进步，尤其是工具可靠性和灾难性零分任务的消除。
2. XBot old 仍是目前质量最高的一次 XBot 结果；当前版本以部分得分为代价，换取
   了更少的耗时、工具调用和工具失败。
3. 当前 XBot 与 OpenCode 的总体得分接近。OpenCode 的 token 和工具效率明显
   更高；XBot 的满分任务更多，并在本次 Office/Business 类任务中领先。
4. 当前最值得逐条审查的 XBot 回归集中在代码修复、本地 API cursor、release
   note 和复现实验包任务。应先阅读这些任务的 transcript，再决定是否修改全局
   prompt 或工具设计。
5. `final-20260801` 没有提供任何可评分证据，不应进入成绩图表。

## 下一轮建议

若需要可发布的框架对比，应从同一个不可变 evaluation commit 和同一个 Docker
镜像重新运行 XBot 与 OpenCode，统一 per-case timeout、provider 配置、任务资产、
并发度和 cache 策略。定向续跑时应追加 invocation manifest，而不是覆盖
`run-manifest.json`。至少增加两个 epoch，才能进一步区分框架差异和模型随机性。

### 如何解释工具失败

不能把所有非零退出都视为同一种问题，也不能为了让指标好看而吞掉失败：

1. **有价值的诊断失败**：例如 `084` 首次 Node 测试准确暴露“createSession
   必须返回新对象”，`087` 首次 pytest 暴露解析器缺陷。这些失败直接缩小问题，
   应保留为真实证据。
2. **可避免的操作失败**：例如对已知可能不存在的多个目录执行一个 `ls`，最后
   一个缺失路径令整条命令返回 2；或者把仅适用于 `filesystem_read` 的参数传给
   `search_text`。这些失败不增加信息，应由更清晰的工具说明和执行纪律减少。
3. **验证器自身错误**：模型编写的检查脚本可能把错误预期写成正确答案，然后
   修改验证器以使其通过。工具成功和自测全绿均不能证明任务完成。
4. **状态型资源被探索消耗**：对一次性或有状态 API 先手工探测、再运行正式实现，
   会永久改变后续观察。此时重复调用不是重试，而是丢失证据。

### 失败与异常轨迹

#### `041-frontend-state-bug`

三次分数稳定在 0.5925-0.6000，但 token 从 126k 到 352k 大幅波动，说明额外
推理没有转化为质量。一条轨迹的 selector 检查报出同一对象原地修改后仍返回
旧值（`200 !== 999`），模型随后又运行整段 heredoc，而没有先隔离缓存身份条件。
另一条轨迹的自建 `_verify.js` 报出 undo 链预期错误（`900 !== 700`），模型选择
修改验证器预期而不是回到产品契约。根因是把“自己写的验证程序通过”误当作验收，
没有用原始需求和现有测试交叉验证隐藏不变量。

#### `048-release-note-changelog`

三次中一条只有 0.59，另外两条接近 0.98。低分轨迹的自建校验全部通过，但 oracle
发现输出泄漏了 embargoed 技术细节或 exploit 信息。它检查了 ID、数量和文件
结构，却没有检查发布边界和安全语义。这是典型的“结构正确、业务验收错误”：
继续增加工具调用不会修复，模型必须先把约束转成可验证的接受条件。

#### `073-research-repro-package`

一条轨迹并发对同一个不存在的 `in/scripts` 调用 list/stat，得到两次等价失败，随后
才从工作区根目录定位文件。另一条轨迹执行 `ls scripts data results`，虽然获得了
部分信息，但最终因缺失目录返回 2。之后 CSV 断言因含逗号字段未加引号失败，模型
使用一次聚焦编辑修复，这属于有效恢复。剩余失分来自报告用词、CSV 契约和过度
声称可复现，而不是文件工具能力不足。

#### `078-local-api-cursor-retry-ledger`

这是最明确的执行流程问题。模型先直接探测有状态 API，消耗了 429、503 和 cursor
事件，再生成正式 fetcher；正式程序只能观察到后续 200，ledger 因而无法记录要求
的恢复事件。反复运行也不能恢复已消费状态。轨迹中还出现先 `ls out/tmp` 后创建
目录、工具链最后一次 `ls` 失败导致整体退出 2、递归 fetcher 失败后再编辑、以及
`filesystem_edit` 的 `old_text` 不匹配后回退 grep。三轮分数完全相同而 XBot token
约为 OpenCode 的 2.9 倍，说明主要问题不是解法缺失，而是没有遵守“第一次关键
操作就通过待验收实现执行”，在不可逆探索和重复验证上消耗了上下文。

#### `084-js-state-type-bug`

该任务三轮均接近满分。首次失败测试准确定位 fresh-object 语义，模型读取实现与
测试后完成修复并收敛。它说明非零退出本身不是坏轨迹；当失败带来新信息且下一步
直接针对该信息时，诊断失败是合理成本。本轮 token 比上轮下降约 39%，但仍高于
OpenCode，后续应优化读取和验证范围，而不是禁止首次失败测试。

#### `087-cli-parser-bug-tests`

质量稳定且 token 比上轮下降约 54%，但重复实验仍从约 103k 波动到 420k。一条
轨迹把 `line_numbers` 错传给 `search_text`，这是跨工具 schema 迁移错误；随后又
以缺少参数的 `--sort` 发起 argparse 探测，并运行多组相似 shell probe。首次 pytest
失败是有效诊断，后续重复探测则是效率问题。相同分数下四倍 usage 波动更接近模型
执行随机性与停止条件不稳，而不是任务复杂度差异。

#### `092-schema-drift-audit`

三轮稳定低分，主要缺失 drift identity、details、severity、schema/data drift、reject

### 本轮修改能证明什么

- **工具集合**：可以证明 schema 成本下降，且这 7 个任务未因缺少工具中断；不能
  证明分数提升，平均分反而下降 0.033。
- **工作区路径规则**：能减少但不能消除错误路径；`092` 是明确反例。
- **shell 退出码说明**：尚未形成稳定行为。`073`、`078` 和未完成 `086` 都出现

- **缓存错误去重**：聚焦测试证明已缓存的长错误不会再次完整嵌入模型 XML，原始
  sidecar 仍保留；但本轮 21 个有效 sample 没有触发超过阈值的 cached error，故
  评估轨迹没有独立复现和证明该修复。

### 后续优先级

1. 先稳定“规划、首次关键执行、基于反馈修复、独立验收、停止”的闭环。尤其要
   明确有状态资源只允许通过正式实现完成第一次关键读取，避免 `078` 类证据消费。
2. 将验收从“我写的脚本通过”收紧为“原始契约逐项满足，并由现有测试、产物检查
   和语义检查交叉证明”，针对 `041`、`048`、`092` 的共同根因，而非新增 case 特判。
3. 工具失败后先分类：参数/路径错误只修正一次；确定性失败先定位根因；预期非零
   必须在命令内部验证后归一为成功；不得无变化重复同一调用。
4. 限制相同信息的重复获取。目录导航、相似 shell probe 和整段验证只有在输入或
   实现发生相关变化后才重跑，以降低 `087` 这类同分数下的 usage 方差。
5. 保留诊断失败，不为降低失败率吞掉退出码。指标应进一步区分首次基线/验收失败
   与参数错误、路径错误、无变化重试，避免优化出虚假的“零失败”。

本轮按要求停止，没有提交代码；`086` 的中断轨迹只用于根因分析，不纳入任何完成
率、分数或成功样本 usage 统计。
