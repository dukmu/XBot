# Team

The optional `team` plugin is disabled by default (`enabled: false`). Enable it in plugin configuration to expose team tools and HTTP operations. It owns member metadata and the board, without adding prompts or commands. Its process facet remains mounted while disabled to preserve fork ownership; stored record references remain readable through persistence.

A team is identified by a caller-provided string within a session. Membership consists of existing thread IDs. Member changes and publication share a serialized boundary; publisher and mentions must be members at the time of the first publication. Board messages are ordered, immutable records. `members` and `count` return current membership and total committed messages. `latest(team, n)` yields the latest n in order; `get(team, ids)` yields each requested ID in caller order with `None` for a missing ID; `after(team, id, n=None)` fixes the durable upper cut at the start and yields subsequent messages up to that cut. All message reads are asynchronous iterators and HTTP reads are NDJSON streams.

HTTP endpoints live below `/sessions/{session_id}/threads/{thread_id}/teams/{team}`: `members`, `members/{thread}`, `count`, `latest?n=`, `after/{message_id}?n=`, `get` (POST an ID array), and `messages` (POST `request_id`, `content`, `mentions`). The request ID is scoped to the publishing thread. Retry with the same request ID and payload returns the original record and retries notifications; changing the payload is a conflict.

The team tools use the ordinary registry and permission guards. Tool publication identity comes from the execution's assistant message and call ID, not a model-supplied sequence. Record selections use the common artifact store and a fixed range, avoiding copies of board contents. Mentioned active threads receive a short runtime notice and the same record reference. Each result reports accepted or failed per target; accepted means submitted, not consumed. Unavailable targets can be retried with `team_retry(team, message_id)`, which uses the original message and mentions without publishing another message. The typed API provides `retry(team, message_id)`; HTTP clients can retry the original request ID and payload. There is no automatic cold delivery. Closing the runtime does not remove stored data; session fork preserves streams and their selections.
